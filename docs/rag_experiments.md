# 2주차: 업로드 문서 RAG와 파라미터·프롬프트 실험

코멘토 2주차 과제(기본 RAG 예제 코드의 프롬프트, chunk_size, overlap, retrieve 파라미터를 바꾸며 결과 차이 확인)를 Bio-GPT에 적용한 기록입니다.
모든 숫자는 실제로 돌린 결과이며, 원본 리포트는 `eval/results/rag_*.md`에 있습니다.

## 요약

| | 시작점: 기본 설정 | 최종 |
|---|---|---|
| 검색 설정 | chunk 400 / overlap 100 / k=3 / similarity | chunk 800 / overlap 0 / k=5 / **hybrid** |
| 프롬프트 | 예제 프롬프트(영어 3줄) | **형식 지정 + Few-shot** |
| 답 검사 | 없음 | 인용·숫자 코드 검사 + AI 검사관 + 틀린 줄 고쳐 쓰기 |
| 정답 근거를 찾아온 비율 | 58% | 83% |
| 최종 답 정답률 (13문항) | 69% | **77%** |
| 출처 없는 문장 | 17줄 | **0줄** |
| 틀린 답을 내보낸 문항 | 4개 | 1개 (나머지 틀린 2개는 '답변 보류'로 막힘) |
| 응답 시간(중앙값) | 1.6초 (작성만) | 8.5초 (검색+작성+검사 전체) |

- 정답률을 가장 많이 올린 것은 **검색 방식(hybrid)**과 **Few-shot 예시**였습니다.
- overlap, mmr, Chain of Thought는 이 문서와 이 모델(Qwen3 8B)에서는 오히려 나빴습니다.
- 실험 중 실제 버그 4개를 찾아 고쳤습니다(아래 5장).

## 1. 무엇을 만들었나

### 1.1 하는 일
연구자가 PDF(예: FDA 허가 라벨, 논문)를 올리고 한국어로 물으면, 문서에서 관련 부분을 찾아 **문장마다 쪽 번호 출처를 달아** 답합니다.
답은 1차 과제 때 만든 검사 단계를 그대로 거칩니다. 출처가 실제 있는지, 숫자가 원문과 같은지, 의미가 맞는지 확인하고, 틀린 줄은 고치거나 뺍니다.

### 1.2 가이드의 8단계가 코드의 어디에 있나

| 가이드 단계 | 하는 일 | 코드 |
|---|---|---|
| 1. 문서 로드 | PDF를 쪽별 텍스트로 읽음 | `rag/loader.py` `load_and_split()` — `PyMuPDFLoader` |
| 2. 분할 | 텍스트를 일정 글자 수의 조각(청크)으로 자름 | 같은 함수 — `RecursiveCharacterTextSplitter(chunk_size, chunk_overlap)` |
| 3. 임베딩 | 청크를 '의미를 나타내는 숫자 목록(벡터)'으로 바꿈 | `bge-m3`(로컬) 또는 `text-embedding-3-small`(OpenAI) |
| 4. 벡터 DB | 벡터를 빠르게 찾을 수 있게 저장 | `FAISS.from_documents()` → `data/index/`에 저장해 재사용 |
| 5. 검색기 | 질문과 가까운 청크 k개를 꺼냄 | `DocIndex.search(k, search_type)` |
| 6. 프롬프트 | 답 쓰는 규칙과 근거를 AI에게 줌 | `prompts.doc_messages()` — 기법 6가지 |
| 7. LLM | 답 작성 | Qwen3 8B(로컬) 또는 GPT-4o |
| 8. 출력 | 검사를 통과한 답만 화면에 | `graph.verify()` → `finalize()` |

청크마다 `DOC:p12-4`(12쪽의 4번째 청크) 같은 이름표를 붙였습니다. 그래서 답의 출처가 실제로 검색해 온 청크인지 코드로 확인할 수 있습니다.

### 1.3 예제 코드와 다르게 한 것

| 예제 코드 | Bio-GPT | 이유 |
|---|---|---|
| `OpenAIEmbeddings()` | 로컬 `bge-m3` (OpenAI 키가 있으면 OpenAI) | 내부 문서를 외부로 보내지 않아도 되게. bge-m3는 다국어 모델이라 한국어 질문으로 영어 문서를 찾을 수 있음 |
| 앱을 켤 때마다 임베딩 | 한 번 만든 색인을 디스크에 저장 | 106쪽 문서 색인에 15~45초 → 두 번째부터 0초 |
| 질문 → 답 한 번에 | 질문 → 답 → **검사 → 고쳐 쓰기** | 틀린 숫자가 사용자에게 나가지 않게 |
| 파라미터를 코드에서 고침 | 화면 사이드바에서 바꿈 | 결과 차이를 바로 비교·시연 |

## 2. 실험 방법

- **문서**: 키트루다(펨브롤리주맙) FDA 허가 라벨 PDF, 106쪽, 약 32만 자 (`samples/keytruda_label.pdf`)
- **문제 13개** (`eval/pdf_golden_set.jsonl`): 용량, 주입 시간, 금기, 이상반응 발생률, 보관 조건, 임상시험 결과 등 12개 + 문서에 없는 질문 1개("한국 식약처 허가 날짜는?" → "확인되지 않음"이 정답)
- 문제마다 정답이 적힌 원문 문장(`evidence`)과 정답 키워드(`keywords`, 예: `3.4%`)를 미리 적어 두고 기계적으로 채점했습니다.

| 지표 | 계산 방법 |
|---|---|
| 검색 적중률 | 정답 원문 문장이 검색된 청크 안에 통째로 들어 있는 문제 비율 (LLM 없이 계산) |
| 정답률 | 정답 키워드가 답에 모두 들어 있는 문제 비율 |
| 근거 일치율 | 답의 줄 중 출처·숫자·AI 검사관 검사를 모두 통과한 줄 비율 |
| 입력 길이 | AI에게 넘긴 글자 수. 길수록 비용(토큰)과 시간이 늘어남 |

실험은 세 단계로 나눴습니다. 한 번에 다 바꾸면 무엇 때문에 좋아졌는지 알 수 없기 때문입니다.

1. **검색만** (`uv run python eval/rag_sweep.py retrieval`): LLM 없이 검색 적중률만 봅니다. 빠르고 비용이 없어서 192가지 조합을 모두 돌렸습니다.
2. **프롬프트만** (`... prompt`): 검색 설정을 고정하고 프롬프트 기법 6가지를 비교합니다.
3. **검색 설정별 실제 답** (`... params fewshot`): 프롬프트를 고정하고 1단계 상위 설정 몇 개로 실제 답을 비교합니다.
4. **최종 확인** (`... final`): 시작점과 최종 앱 전체 흐름을 비교합니다.

## 3. 1단계: 검색 파라미터 (LLM 없음)

원본: `eval/results/rag_retrieval_20261005_1408.md`

### 3.1 주요 결과

| chunk_size / overlap | 검색 방식 | k | 검색 적중률 | 입력 길이 | 못 찾은 문제 |
|---|---|---:|---:|---:|---|
| 400 / 100 (예제 값) | similarity | 1 | 17% | 370자 | 10개 |
| **400 / 100 (예제 값)** | **similarity** | **3** | **58%** | 1,110자 | D02 D04 D05 D11 D12 |
| 400 / 100 | similarity | 5 | 58% | 1,810자 | 〃 |
| 400 / 100 | mmr | 3 | 25% | 1,120자 | 9개 |
| 400 / 100 | hybrid | 3 | 67% | 1,098자 | D02 D04 D05 D11 |
| 200 / 0 | similarity | 3 | 50% | 415자 | 6개 |
| 1500 / 0 | similarity | 5 | 75% | 6,524자 | D04 D05 D12 |
| 800 / 200 | hybrid | 5 | 67% | 3,594자 | D04 D05 D06 D07 |
| **800 / 0** | **hybrid** | **5** | **83%** | 3,701자 | D04 D05 |
| 800 / 0 | hybrid | 8 | 92% | 5,944자 | D04 |

### 3.2 파라미터별로 알게 된 것

**chunk_size (청크 크기)**
- 200자처럼 작게 자르면 표나 문단이 중간에 잘려 정답 문장이 두 청크로 나뉩니다(적중률 50%).
- 800~1500자로 크게 자르면 정답이 한 청크에 통째로 들어갈 가능성이 높아집니다. 대신 AI에게 넘기는 글이 길어집니다.
- FDA 라벨은 표가 많아 400자로는 표 한 칸("Adult patients with melanoma / 200 mg every 3 weeks / or 400 mg every 6 weeks")도 잘리는 경우가 있었습니다.

**chunk_overlap (겹침)**
- 겹침은 '잘린 경계에 걸친 문장'을 살리려는 장치입니다. 그런데 이 문서에서는 크기별 평균 적중률이 겹침 없음 47~59%, 겹침 있음 42~55%로 차이가 없거나 오히려 낮았습니다.
- 겹치면 청크 수가 늘어(800자 기준 460개 → 539개) 비슷한 청크끼리 상위 k자리를 나눠 갖게 됩니다. 그러면 정답 청크가 밀려나는 경우가 생겼습니다(800/200 hybrid k=5에서 D06 D07을 놓침).
- 문제 12개라 몇 문제 차이로 숫자가 크게 흔들립니다. "overlap이 해롭다"가 아니라 "이 문서에서는 효과가 확인되지 않았다"가 정확한 결론입니다.

**k (가져올 청크 수)**
- k=1은 17%로 크게 떨어집니다. 정답 청크가 1등이 아니라 2~3등으로 잡히는 경우가 많기 때문입니다.
- k를 3에서 5, 8로 늘리면 적중률은 오르지만 입력이 길어집니다. 3단계에서 보듯 너무 많이 주면 작은 모델이 오히려 헷갈립니다.

**검색 방식**
- `similarity`: 질문과 의미가 가장 가까운 k개.
- `mmr`: 가까우면서 서로 내용이 겹치지 않는 k개. 다양성을 챙기다 정답 청크를 밀어내서 가장 나빴습니다(25%).
- `hybrid`(직접 추가): 의미 검색(FAISS) 결과와 키워드 검색(BM25) 결과를 순위로 합칩니다. "KEYNOTE-054", "1019 patients" 같은 고유 이름과 숫자는 의미 검색이 놓치기 쉬운데, 키워드 검색은 정확히 찾습니다. 합치는 방법은 RRF(각 결과의 순위 r에 대해 1/(60+r)을 더함)로, 두 검색의 점수 단위가 달라도 순위끼리는 합칠 수 있습니다.

**질문을 영어로 바꿔 검색**
- 문서가 영어라 LLM으로 질문을 영어 검색어로 바꾸는 방법도 시험했습니다. similarity에서는 조금 도움이 됐지만(k=8: 58% → 75%), hybrid에서는 일정하지 않았습니다. 번역에 1~2초가 더 들어 기본값에서는 껐고, 화면에서 켤 수 있게 두었습니다.

### 3.3 끝까지 못 찾은 문제
- **D04 금기**: 정답이 요약 페이지의 "CONTRAINDICATIONS ---- None. (4)" 한 줄뿐입니다. "없음"은 의미 검색으로 찾기 가장 어려운 답이라, 거의 모든 설정에서 놓쳤습니다.
- **D05 폐렴 발생률**: 같은 쪽에 '호지킨 림프종 환자에서 폐렴 8%'라는 다른 수치가 있어서 그 청크가 먼저 잡혔습니다.

## 4. 2단계: 프롬프트 기법 (검색 고정: 800/0, k=5, hybrid)

원본: `eval/results/rag_prompt_20261005_1435.md`. 프롬프트 기법(역할 지정·형식 지정·Few-shot·CoT)을 하나씩 더해 같은 검색 결과로 비교했습니다. 프롬프트 내용은 `bio_gpt/agent/prompts.py` 5절에 있습니다.

| 기법 | 설명 | 정답률 | 근거 일치율 | 출처 없는 줄 | 작성 시간 |
|---|---|---:|---:|---:|---:|
| baseline | 예제 코드 프롬프트 그대로 | 77% | 0% | 19 | 1.2초 |
| v1.5 | 기존 Bio-GPT: 역할 지정 + 규칙 목록 | 77% | 73% | 1 | 5.1초 |
| format | 형식 지정 기법(#명령문 #제약조건 #입력문 #출력형식) + 역할 지정 | 69% | 77% | 0 | 5.1초 |
| **fewshot** | format + 예시 3개 | **92%** | 65% | 0 | 5.6초 |
| cot | format + Chain of Thought("차근차근 생각해 봅시다", 생각 과정 → 답변) | 62% | 50% | 0 | 6.4초 |
| fewshot_cot | format + 예시 3개 + CoT | 85% | 62% | 0 | 10.0초 |

### 4.1 알게 된 것

**baseline**은 숫자는 꽤 맞히지만 출처를 하나도 달지 않아 검사할 방법이 없습니다. 답이 맞는지 사용자가 원문을 직접 찾아봐야 합니다.

**Few-shot이 가장 좋았습니다.** 예시 3개는 일부러 다른 유형으로 골랐습니다. ① 숫자 하나를 답하는 문제, ② 두 가지를 묻는 문제, ③ 문서에 답이 없는 문제("확인되지 않음")입니다.
작은 모델은 "규칙"보다 "보기"를 더 잘 따라 했습니다. 예시 약은 가상의 `ZX-101`로 만들어, 예시 내용이 실제 답에 새는지 코드로 검사했습니다(누출 0건). 1차 과제 때 v1.6에서 예시 문장이 답에 새던 문제를 이렇게 막았습니다.

**형식 지정 기법의 [ ] 자리 표시가 인용 [ ]와 충돌했습니다.** 가이드는 출력 형식을 `[사실 1]`처럼 대괄호로 표시하라고 합니다. 그런데 우리는 출처도 `[DOC:p12-4]`로 대괄호를 씁니다. 처음 버전에서는 모델이 문장을 [ ] 안에 넣고 출처는 괄호 밖에 써서 인용 검사에서 전부 걸렸습니다. 채울 자리를 `( )`로 바꿔 해결했지만, 8B 모델은 여전히 `(사실 1)`을 그대로 베끼는 경우가 있었습니다.

**CoT는 이 모델에서 가장 나빴습니다.** 생각 과정은 그럴듯하게 썼습니다. 예를 들어 "근거 찾기: DOC:p12-4 → 'Immune-mediated colitis occurred in 1.7%'"처럼 원문을 정확히 찾아 적었습니다. 그런데 정작 답변 부분에서 숫자를 빠뜨렸습니다("- 면역 매개 대장염 발생률 [DOC:p12-4]"). 출력이 길어져 시간도 늘었습니다. 생각 과정은 화면의 "🧠 판단 과정" 칸에서 볼 수 있게 남겨 두었습니다. GPT-4o 같은 큰 모델에서는 결과가 다를 수 있습니다(아직 시험 안 함).

**근거 일치율과 정답률은 다른 것을 잽니다.** Few-shot은 정답은 많이 맞혔지만, 질문 외의 사실을 덧붙이다 틀린 줄이 생겼습니다. 예를 들어 '희석한 용액은 96시간'을 '바이알은 96시간'으로 쓴 경우입니다. 이런 줄은 AI 검사관이 잡아 최종 답에서 빠집니다.

## 5. 3단계: 검색 설정별 실제 답 (프롬프트 고정: Few-shot)

원본: `eval/results/rag_params_20261005_1455.md`

| chunk_size / overlap | k | 검색 | 검색 적중률 | 정답률 | 작성 시간 | 입력 길이 |
|---|---:|---|---:|---:|---:|---:|
| 400 / 100 (예제 값) | 3 | similarity | 58% | 69% | 2.6초 | 2,645자 |
| 400 / 100 | 5 | similarity | 58% | 69% | 3.5초 | 3,473자 |
| **800 / 0** | **5** | **hybrid** | 83% | **92%** | 2.1초 | 5,310자 |
| 800 / 0 | 8 | hybrid | 92% | 85% | 7.3초 | 7,748자 |
| 400 / 0 | 8 | hybrid · 영어 검색 | 83% | 85% | 4.6초 | 4,760자 |
| 1500 / 0 | 5 | similarity | 75% | 85% | 7.9초 | 8,059자 |

- 검색 적중률이 높을수록 대체로 정답률도 높았습니다. **검색이 못 찾으면 프롬프트로는 살릴 수 없습니다.**
- 그런데 k=8은 적중률이 가장 높은데도 정답률이 떨어졌습니다. 정답과 비슷한 다른 수치(다른 암종의 발생률 등)가 함께 들어와 8B 모델이 헷갈렸습니다. **많이 가져오는 것과 잘 가져오는 것은 다릅니다.**
- 그래서 기본값을 **800 / 0 / k=5 / hybrid + Few-shot**으로 정했습니다(`rag/index.py` `DEFAULTS`).
- 작성 시간은 같은 설정에서도 실행마다 2~6초씩 흔들렸습니다(2단계 5.6초 vs 3단계 2.1초). 시간은 경향만 보는 것이 맞습니다.

## 7. 남은 한계와 다음 단계

- **문제 13개는 적습니다.** 한 문제가 8%포인트라 작은 차이는 우연일 수 있습니다. 문서 종류(논문, 국내 허가 문서)와 문제 수를 늘려야 합니다.
- **"없음"이 답인 질문**(금기 없음 등)은 검색이 가장 약합니다. 문서의 목차 구조(1 적응증, 4 금기 …)를 청크 정보에 넣어 섹션 이름으로도 찾게 하는 방법을 시험해 볼 수 있습니다.
- **검사관의 약어 오탐**(cHL ↔ 고전적 호지킨 림프종): 검사관에게도 용어 사전을 함께 주는 방법을 시험할 수 있습니다.
- **GPT-4o로는 아직 돌려 보지 않았습니다.** `.env`에 `OPENAI_API_KEY`만 넣으면 같은 실험을 그대로 돌릴 수 있습니다. 특히 CoT 결과는 큰 모델에서 달라질 가능성이 큽니다.
